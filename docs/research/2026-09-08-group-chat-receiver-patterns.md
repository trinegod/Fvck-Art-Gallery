# Group-chat receiver patterns

Researched September 8, 2026 for NODEINE's **The District** membership question, reliable receiver-side invitations, and requested `@person` / `@everyone` mentions. This is primary-source research and local source inspection, not a live multi-account test or an implementation promise.

## What “1 member after inviting two people” can mean

At this source-inspection checkpoint, `create_group_conversation` creates the owner's membership and separate pending invitations. `respond_to_group_invite` adds a recipient to `conversation_members` only when that recipient accepts. The inbox counts actual membership rows. Therefore **1 member + 2 pending invitations** is a valid state; “3 members” would be false before acceptance. The actual District records require separate live verification. Sources: [group creation and invitation RPCs](../../supabase/group-chat-expansion.sql), [inbox and invite receiver UI](../../app/messages/messages-view.tsx).

Crucially, the current message SELECT policy checks conversation membership, not `joined_at`. Becoming a member therefore grants access to earlier stored messages, subject to the existing personal clear cutoff; that cutoff is a presentation preference, not a history-authorization boundary. Automatically accepting invitations would change both participation and prior-history exposure. Sources: [membership-wide message policy](../../supabase/messages.sql), [history queries](../../lib/message-history.ts), [clear semantics](../../supabase/message-controls.sql).

## Recommended NODEINE contract

These are project recommendations inferred from the comparison, not claims that these features already exist.

1. **Deliver invitations automatically; count membership honestly.** Creating a group should immediately persist invitations and make a labeled invitation available to each recipient. Show the owner “1 member · 2 invited,” each pending recipient, and recoverable delivery/loading errors. The receiver should see the group identity, inviter, relevant history disclosure, and clear Join / Decline actions. Invitation receipt, accepted membership, message delivery, and Seen are four different milestones.
2. **Choose direct-add behavior explicitly.** If the owner wants instant membership instead, document who may add whom, the receiver's prior consent or privacy controls, the exit/report path, notification behavior, and historical access. A selected profile is not evidence of receiver consent. Do not silently convert existing pending invitations merely to increase a displayed count.
3. **Disclose existing history access.** Under current membership-wide RLS, describe that joining allows earlier group messages to be read. A future “messages since joining” or selected-history-sharing mode needs server/storage authorization design and tests; hiding old rows only in the interface is insufficient. The research does not authorize narrowing or expanding existing members' access.
4. **Make mentions identity-based and visible.** `@person` should select an accepted member by stable profile ID, with name/username disambiguation. Store validated mention metadata; plain quoted text, pasted display names, and email addresses should not accidentally notify people. Pending invitees, outsiders, and departed members are not valid notification recipients. Matrix's metadata model and Discord's anti-phantom-ping rule are useful implementation references, not code to copy wholesale.
5. **Bound `@everyone`.** Start with owner/admin permission, a clearly labeled action, and one notification outcome per eligible recipient/message. Re-check membership and permission on the server at send time. A textual `@everyone` token alone must not bypass authorization. Treat rate limits and edit/retry deduplication as part of this feature, not later polish.
6. **Keep the receiver's mute meaningful.** Preserve NODEINE's current suppression of new notifications while muted unless an explicit receiver-controlled mentions override is designed and approved. Mention highlighting, unread badges, in-app Activity, and operating-system push are separate behaviors; never promise push merely because a message was saved.

## Priorities and verification boundary

Immediate work is the real recipient's invitation discovery, Join/Decline, accurate counts, and disclosed history access. Structured `@person` / `@everyone`, direct-add privacy preferences, invitation reminders/expiry, room-history modes, and a mentions-only inbox are a **broader feature backlog** until implemented and verified. Reference-product encryption and delivery guarantees do not transfer to NODEINE.

Use the [receiver master prompt and scenario checklist](../prompts/group-chat-receiver-master-prompt.md) for implementation and audit. A screenshot, successful owner-side invite, unit test, or source-present RPC does not establish a completed receiver workflow. No receiver login, invitation response, private-history access, notification delivery, native-phone interaction, or mention fan-out was tested during this research.

Repository references above are pinned to the retrieved commits; product announcements describe documented behavior rather than universal device rollout.
