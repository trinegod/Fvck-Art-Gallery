# NODEINE usability and reliability audit — 2026-09-06

> Follow-up: the owner approved repairs after this read-only audit. See [repair verification](2026-09-06-repair-verification.md) for the local implementation and tested outcomes. The original findings below remain the historical baseline; they do not describe deployment status after subsequent releases.

## Scope and outcome

Read-only audit requested by the owner, with three parallel agents covering navigation, creator/account flows, and automated validation. The main agent tested the public production app at https://nodeine.vercel.app in the browser. Local source reviewed at commit `893cfbe2009d9a760a6a00813f61671531f94552`.

The app has functioning public browsing journeys, but is not ready for an “everything works perfectly” claim. Prioritize reliability and navigation consistency before another major feature. The best bounded feature refinement is an owner-only **Your work / Drafts** entry inside Create, not another permanent bottom-navigation icon.

No application code, accounts, posts, messages, database records, deployment, or Git history were changed. This report is the only new repository artifact from the audit. Existing untracked `docs/research/` files were preserved.

This is an engineering and heuristic usability audit, not independent user research. No user-growth, usability-improvement, conversion, or task-success metrics are claimed.

## Menu assessment

The Explore / Create / You grouping is understandable, and Feed stays accessible. The persistent two-level dock is visually heavy:

| Browser viewport | Dock bounds | Share of viewport height | Measured controls |
| --- | --- | --- | --- |
| 390 × 844 | 366 × 122, 12px outer gutter | 14.5% | Section tabs 93 × 44; destination links about 92 × 56 |
| 320 × 740 | 296 × 122, 12px outer gutter | 16.5% | Section tabs about 70 × 44; Create links about 68 × 56 |

These are browser viewport measurements, not a physical-phone or safe-area certification. The measured dock controls meet the project's 44px target. Keyboard ArrowRight switched Explore to Create successfully; ArrowLeft returned it. Screenshots were inspected at both mobile sizes.

Recommended design hypothesis: keep one compact, labeled bottom row for **Feed / Explore / Create / You**, with section destinations in the selected section's page content or a contextual horizontal strip near its heading. Avoid a More drawer, unlabeled icons, and gesture-only discovery. Keep the existing art-first dark styling. Prototype and compare before adopting this change; reduced dock height is a target, not a measured improvement yet.

Navigation also needs one consistent structure across pages. At desktop width, the creator profile header exposes Archive, Discover, Saved, Inbox, Activity, and Studio, but no Feed, Threads, or Forge. The feed's sidebar exposes a different set. The Discover route also opens with another For You / Discover / Following selector, duplicating the feed's vocabulary. These observations support simplifying the overall information architecture rather than merely shrinking icons.

## Findings

P1 means fix first because of private-state handling. P2 means a consequential workflow defect. Evidence categories distinguish live browser reproduction, local synthetic execution, and static code inspection.

### 1. P1 — A delayed Activity load can redisplay private previews after logout

- Evidence: **synthetic execution of the actual callback**, plus source review; not reproduced with real private data.
- Source: `app/activity/activity-view.tsx:100–164`, especially the unguarded setters at 158; logout clearing at 173–185.
- Reproduction: start account A's activity load; delay the related-data results; simulate logout so state is cleared; resolve the old request. The callback sets A's rows and `ready` again.
- Result: synthetic prior-account notifications reappeared after the synthetic logout. This is stale client state, **not evidence of a server-side authorization bypass**.
- Acceptance check: invalidate pending requests on logout/account change; no old-account result may commit. Test delayed success and failure after sign-out and account switching.
- Related unverified risks: Saved has a similar unversioned load; private Thread detail/composer auth transitions need separate tests.

### 2. P2 — A cold feed does not attach its scrolling observers

- Evidence: **live production reproduction and actual-component hook harness**.
- Source: `app/feed/feed-view.tsx:352–405`, effect dependency lists at 386 and 404.
- Reproduction: open a fresh `/feed`; allow loading to finish; scroll to the visible Load 12 more signals button without switching modes.
- Live result: 12 articles remained at the bottom, and the URL remained bare `/feed`. Clicking Load 12 more signals increased the count to 24.
- Local cause demonstration: initial loading render has no cards or sentinel; after loading, 12 cards render, but the dependency lists do not change and zero observers are constructed.
- Impact: automatic pagination and current-card context are not initialized on this path. Manual pagination works.
- Acceptance check: after asynchronous data/auth loading, scrolling updates the current signal and reaching the sentinel loads the next batch without a mode switch.

### 3. P2 — Browser Back to bare `/feed` retains Discover mode

- Evidence: **live production reproduction and exact-handler execution**.
- Source: `app/feed/feed-view.tsx:225–231`.
- Reproduction: new tab at `/feed` → choose Discover → browser Back.
- Live result: URL returns to `/feed`, but the page title remains Discover rather than For you.
- Cause: the history handler only handles an explicit valid `mode`; it does not restore the default when the parameter is missing.
- Acceptance check: missing/invalid modes resolve to the default, with selection, heading, list, and URL consistent after Back/Forward. Also test same-route Link navigation because `initialMode` is only an initializer.

### 4. P2 — Following related artwork loses the feed return route

- Evidence: **live production reproduction and component rendering**.
- Source: `app/components/artwork-signal-trail.tsx:52`; return fallback in `app/artwork/[id]/page.tsx:274–276`.
- Reproduction: feed → Ashigara 002 → Signal Trail's Ashigara 001.
- Live result: first artwork offers Back to feed with mode/signal; related artwork's plain URL drops both parameters and offers Back to archive (`/`).
- Related source-confirmed gaps: response cards at `app/threads/thread-card.tsx:12`, used by `app/threads/[slug]/thread-detail.tsx:317`, and fork-source links at `thread-detail.tsx:87` also drop context. Those branch variants were not live-tested with created fixtures.
- Acceptance check: multi-hop artwork and Chronicle branches preserve the originating feed mode and signal. Distinguish a dedicated feed-return action from ordinary browser Back.

### 5. P2 — Conversations over 200 messages omit the newest existing messages

- Evidence: **actual extracted loader executed with the installed PostgREST client and 205 synthetic messages**; no network writes.
- Source: `app/messages/messages-view.tsx:615–641`.
- Reproduction: reopen a conversation containing more than 200 existing messages.
- Local result: oldest messages 1–200 displayed, 201–205 omitted, then fake `last_read_at` advanced past all 205.
- Cause: ascending order with `limit(200)`, no older/newer pagination, followed by marking the conversation read at now.
- Acceptance check: load the latest page, support older-history pagination, and advance read state only appropriately for displayed/read messages. Cover incoming-message races.

### 6. P2 — Opening an Activity item never persists its individual seen state

- Evidence: **installed PostgREST client with injected fake fetch**, no network writes.
- Source: `app/activity/activity-view.tsx:275–279`.
- Reproduction: open an unread item, return/reload Activity.
- Local result: exact `void ...update().eq().eq()` chain issued zero requests; awaited control issued one fake request. The query is lazy and is never awaited or consumed.
- Impact: optimistic UI suggests success, but individual seen state is not saved. Mark all seen is separately awaited and is not this defect.
- Acceptance check: a completed update persists, and a failed update restores honest state or shows an error without silently claiming success.

### 7. P2 — Private Thread drafts have no in-app reopening list

- Evidence: **static code-confirmed workflow gap**; deliberately did not create a live draft.
- Source: default `visibility: "draft"` at `app/threads/thread-composer.tsx:63–68`; save redirect at 300–309; public-only listing at `app/threads/page.tsx:18` and `lib/world-threads.ts:341–350`.
- Reproduction: save a default private draft, leave its detail/editor, then try to reopen it through Threads, Studio, Saved, or the creator profile.
- Result: no owner draft index exists; recovery requires retaining the URL or browser history. This is a discoverability dead end, **not demonstrated database loss**.
- Acceptance check: an owner-only Drafts list inside Create can reopen drafts across visits, while other users and signed-out visitors cannot list/read them. Keep published and private states explicit.

### 8. Navigation consistency — Signed-out New Thread removes the mobile dock

- Evidence: **live production and source confirmation**.
- Source: `app/threads/thread-composer.tsx:324–333` and the `ComposerStatus` shell at 636 onward.
- Reproduction: signed out → Create → New Thread.
- Result: Sign in to draw a path appears, but Primary app navigation count is zero. Forge, Saved, Inbox, Activity, and Studio sign-in screens retain the dock.
- Impact: this route breaks the expected persistent Feed escape path. Browser Back and the NODEINE Archive link remain available; it is not a total lockout.
- Acceptance check: shared navigation and a meaningful exit remain available in loading, signed-out, empty, not-found, and error states.

## Recommended next increment

1. Fix and regression-test private-state invalidation, individual seen updates, and message pagination/read position.
2. Repair feed loading/history/multi-hop return behavior and keep navigation consistent on access/error screens.
3. Add a small owner-only Your work / Drafts area under Create so existing Thread drafts can be resumed. Do not imply Forge revisions are persisted until that capability actually exists.
4. Prototype the slimmer single-row dock using the existing DESIGN.md art-first and accessibility constraints. Resolve duplicate Discover/For You terminology and desktop/mobile destination inconsistencies together.
5. With an explicitly designated test account/environment, exercise authenticated create → save → leave → reopen → edit flows and mutation failure recovery. Add these journeys to automated UI/integration coverage.

The next milestone should be: **easy to enter, easy to resume, easy to leave without losing context**. Real image generation remains a separate scoped project; this audit does not enable it.
